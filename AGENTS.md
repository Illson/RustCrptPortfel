# dotnetCrptPortfel — инструкции для агентов

dotnetCrptPortfel — веб-приложение на ASP.NET Core/.NET 11 и React для оценки криптопортфеля, а также автономная CLI для расчётов по локальным TSV. Карта кода и команды запуска и тестирования описаны в [README.md](README.md). Поддерживай эти сведения при изменении поведения, структуры и команд.

## Рабочий цикл

- Перед правками проверь корень репозитория, `git status --short --branch`, `git diff` и `git diff --cached`. Сверь текущую ветку и новые файлы из `git status`. Сохраняй чужие изменения.
- До базового коммита выполняй стартовую задачу в текущем checkout. После него начинай новые задачи в отдельных worktree и ветках `codex/<задача>` от обновлённой `origin/main`. До первой публикации используй базовый коммит локальной `main`. Для продолжения задачи используй её ветку и worktree. При detached HEAD создай ветку до первого коммита. Если обновить `origin/main` не удалось, укажи, от какой версии продолжил работу.
- Если задача связана с GitHub, проверь открытые issues и PR по теме, чтобы учесть уже принятые решения и параллельную работу. При недоступности GitHub продолжай локальные шаги, для которых хватает контекста.
- Для сложной задачи зафиксируй цель, критерии приёмки и риски в существующем issue, PR или документации задачи. Обычные технические решения принимай самостоятельно. Уточняй неоднозначности, если от ответа зависят пользовательские данные, внешний контракт или выпуск.
- Делай небольшие изменения, которые можно проверить через штатный вход в приложение или модуль. При исправлении воспроизводимой ошибки добавляй регрессионный тест. При изменении формата данных проверь чтение существующих данных и поведение при прерванной записи или повторном запуске.
- Сначала выполняй целевые проверки, затем общие команды проекта из `README.md`, когда они появятся. Просмотри весь свой diff и содержимое новых файлов. Проверь пробельные ошибки через `git diff --check`, а для новых неотслеживаемых файлов используй `git diff --no-index --check` с пустым файлом. Перед коммитом добавь в индекс файлы задачи и выполни `git diff --cached --check`.

## Контекст для следующих задач

- Держи общие правила здесь, команды и карту кода в `README.md`, а подробности форматов и интеграций рядом с соответствующим кодом. В документации используй относительные ссылки на существующие файлы. Добавляй вложенный `AGENTS.md`, когда у каталога появляются собственные устойчивые правила.
- Для решений с долгим сроком жизни фиксируй причину выбора и условия, при которых решение нужно пересмотреть. Для внешнего контракта описывай входные данные, результаты и ошибки. При изменении поведения обновляй связанные примеры и проверки в той же задаче.
- По возможности отделяй вычисления от ввода-вывода. Для сценариев с внешними сервисами используй синтетические данные и воспроизводимые тесты. Рабочие токены, ключи и частные выгрузки оставляй в предназначенном для них локальном хранилище. В примерах, тестах, логах и запросах к LLM используй синтетические или обезличенные значения.
- Храни временные данные и результаты экспериментов в каталоге задачи. После проверок удаляй созданные задачей временные файлы, если они больше не нужны. Сохраняй запрошенные артефакты и пользовательские данные.

## Для задач по учёту криптоактивов

- Для сумм, количеств активов и курсов используй точное представление. Фиксируй правила округления на границах ввода, хранения, расчёта или отображения там, где округление применяется.
- Храни вместе с котировкой актив, валюту цены, время и источник. Перед агрегацией приводи суммы к общей валюте. Отсутствующие или устаревшие котировки обрабатывай явно и проверяй это тестами с фиксированным временем.

## Публикация и передача работы

- Если задача предусматривает публикацию, запушь рабочую ветку в `origin` и проверь SHA на GitHub. Если на GitHub уже есть базовая ветка `main`, открой или обнови PR. В конце заголовка PR укажи номера связанных issues, например `Уточнить формат котировки (#17, #21)`. Используй `Closes #17`, когда выполнены все критерии issue. Для частичной работы укажи связь без закрытия.
- Проверь результат CI для актуального SHA, если в репозитории есть CI. Слияние, теги и выпуск выполняй по отдельной просьбе пользователя.
- При ревью привязывай замечания к строкам актуального diff. При повторной проверке укажи, какие замечания закрыты исправлениями в проверенном SHA.
- В итоге укажи, что изменилось, какие проверки прошли и какие остались непроверенными. Для опубликованных изменений добавь ветку, SHA и ссылку на PR. При сбое публикации сохрани локальный результат и укажи конкретную причину.
