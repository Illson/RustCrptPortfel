# Ревью по ТЗ 1.1

Этот документ описывает прежний учебный сценарий и его проверки. В текущей сборке пользовательский интерфейс, API и worker этого сценария сняты; рабочий сценарий — [локальный профиль с портфелями из файлов](portfolio-profile.md).

Цель: довести до проверяемого состояния сценарий «снимок → метрики → исследование → проверка → лента», не выдавая учебные данные за сведения из личного портфеля. Отдельно проверяются отказ интеграции, точность, повторное выполнение и запуск приложения.

**Уточнение стека:** выбран SQLite с EF Core 11 для однопользовательского запуска на одном хосте, в том числе в Production. Критерии перехода: нет отдельного сервера БД или второго драйвера, старый файл обновляется без потери данных, конкурентные запросы не создают дублей, сбой записи не оставляет частичную публикацию. Пересмотреть выбор придётся при необходимости нескольких хостов или большом объёме конкурентных записей.

## Формулы и хранение

- По замечаниям PR #1: проверка права на персонализацию, времени, состава и профиля выполняется в транзакции резервирования синтеза и повторно при публикации. Если проверка до отправки провалилась, провайдер не вызывается и бюджет синтеза не резервируется. Сетевой обрыв или тайм-аут страницы оставляет прежний состав, записывает неуспешную попытку и отключает персонализацию; отмена вызывающей стороны не меняет результат последней проверки.
- `FetchedAt` наблюдения — первая загрузка данной ревизии. Времена повторных подтверждений хранятся отдельно и используются только начиная с момента соответствующей проверки. Для старых записей без истории точка отсчёта — сохранённый `FetchedAt`; предшествующие ему проверки восстановить нельзя. Сумма месяца с устаревшим дневным значением остаётся устаревшей и не участвует в сравнении.
- Для одного `(актив, источник, ID события)` версия расписания `vN` упорядочивается по числу N **до** отбора по окну. Два разных транша одной аллокации должны иметь разные ID. Несовместимые записи одной версии и различающиеся записи без сопоставимых версий дают `conflict` в затронутом окне.
- Разные идентификаторы траншей одного источника сохраняют кратность даже при совпадении суммы и даты. Для одинаковой аллокации сверяется число эквивалентных записей разных источников; расхождение даёт `conflict`. При ошибочном объёме в обращении проценты не рассчитываются, абсолютные суммы расписания остаются доступны.
- Снимок портфеля с `SourceAsOf > FetchedAt` отклоняется как `invalid_snapshot`. Состояния одного проектного события упорядочиваются по `AnnouncedAt`: более ранний повтор не отменяет перенос, противоречие на одном времени — `event_conflict`.
- При частичной загрузке рынков новые наблюдения заменяют прежние с тем же ID, а пропущенные пары сохраняются. Покрытие остаётся `partial` до полного ответа этого источника; доступны наблюдаемые объёмы, но не доли площадок. Более старый пакет не заменяет более свежий.

- Суммы потоков вычисляются по непересекающимся завершённым дням UTC. Пропуск даёт `partial`; сравнения доступны только при сопоставимом покрытии. MTD сравнивается с тем же числом дней предыдущего месяца, если период существует. Для неположительной базы доступна абсолютная разница, а не процент.
- Проценты округляются до восьми знаков методом midpoint-to-even. Линейные сегменты интегрируются до 96 дробных знаков, полностью попавшие сохраняются без округления. На границе входа `ExactNumber` допускает до 96 дробных знаков и не более 257 символов. `double` и .NET `decimal` для этих данных не используются.
- В SQLite задания и версии ленты разнесены по таблицам и имеют ограничения уникальности; состав, наблюдения, настройки, журналы и снимки хранятся как JSON-текст по владельцу. Запись сериализуется транзакцией SQLite. Чтение портфеля, очереди и ленты одним SQL-запросом видит один и тот же снимок БД. Это решение для одного хоста, не распределённая очередь.
- Секреты AI не нужны демо и не попадают в bundle. Бюджет в тестируемом сценарии — локальная оценка: неизвестная цена не становится нулём, неопределённый вызов не выдаётся за исполненный. Сверка неопределённых резервов с провайдером и управление бюджетами через UI не подключены.

## Что ещё требуется до приёмки

1. Подтвердить **оба** договора CMC и прогнать вход/отзыв доступа и добавление, изменение, удаление на разрешённом тестовом портфеле.
2. После подтверждения подключить к worker источник личного портфеля и регулярный сбор рабочих данных; завершить проверку тарифов, расписаний, источников проектов и UI подтверждения сопоставлений.
3. Подключить реальные AI-настройки: безопасное хранение ключей, подтверждение возможностей конкретного аккаунта, вход ChatGPT для поддержанного размещения и эксплуатацию бюджетов. Live-workflow не активируется через демо; локальная проверка не выдаётся за работу с платным маршрутом.
4. Полный production end-to-end и Compose-прогон остаются отдельными проверками. В текущем окружении Docker Desktop вручную поставлен на паузу, поэтому проверена только конфигурация Compose.

## Локальный прогон

- Строгая сборка на SDK `11.0.100` и штатном runtime `11.0.0`, `net11.0` и `runtime-async=on` во всех собственных проектах.
- Все 13 тестов CLI и веб-набор с временной SQLite. Проверены повторная и неполная синхронизация, миграция прежних данных, ограничения БД, конкурентная постановка и откат частичной публикации, формулы, контракты провайдеров, отмена и бюджет.
- Frozen frontend lock, сборка Vite, три сценария Playwright против локальных API и worker (включая ширины 390 и 1440 px и HTTP-проверку). Отдельный запуск Production не предоставил демо-вход даже с `Demo__Enabled=true`.
- Те же команды записаны в [workflow CI](../.github/workflows/checks.yml).
